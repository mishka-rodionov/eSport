# Competra Android vs pysport (SportOrg): сравнение функционала (v2, по исходникам)

> Обновлено после клонирования `https://github.com/sportorg/pysport.git` в `/Users/rodionov/desctop_projects/pysport` и прямого чтения кода (`sportorg/models/memory.py`, `sportorg/models/start/*`, `sportorg/models/result/*`, `sportorg/modules/*`, `sportorg/gui/dialogs/*`). Первая версия сравнения опиралась только на документацию (readthedocs/changelog) — часть догадок здесь подтвердилась, часть скорректирована, и нашлось много деталей, которых в документации просто не было.

## TL;DR

- **pysport** — desktop-приложение (Python/Qt, Windows) для оператора за компьютером на точке старта/финиша. Работает с аппаратными станциями отметки (SPORTident/SFR/Sportiduino/RFID Impinj/Huichang/Srpid) по кабелю/USB. Движок расчёта результата и стартовых форматов — очень глубокий (см. раздел 2): пуристский софт под ориентирование/рогейн/ARDF со всеми историческими форматами гонок.
- **competra-android** — мобильное NFC-приложение с облачным offline-first backend и слоем «платформы» (пользователи, клубы, рейтинг серий, дневник тренировок), которого у pysport нет вообще — это принципиально другой продукт (не просто «десктоп для одного мероприятия», а сервис на несколько соревнований и сообществ).

## 1. Совпадающий функционал

| Область | pysport | competra-android |
|---|---|---|
| Импорт дистанций | IOF XML (полный: entry/start/result/competitor list), OCAD Courses v8, CSV Winorient, variation data (варианты этапов) | IOF XML (из `mapper`), только импорт |
| Группы участников | `Group`: name, course, min/max age или year, start_interval, start_corridor, max_time | `ParticipantGroup`: title/gender/minAge/maxAge, distanceId, timeLimitMinutes |
| Статусы участника | `ResultStatus` — 18 значений (см. ниже) | `ResultStatus` — 6 значений: REGISTERED/STARTED/FINISHED/DSQ/DNS/DNF |
| Форматы дистанции | Классика, рогейн/score (`ControlPoint.score`), маркированная трасса, ARDF | `OrienteeringDirection`: FORWARD / BY_CHOICE (score с штрафом за минуту) / MARKING |
| Источник стартового времени | Станция, вручную, из протокола, из предыдущего этапа (pursuit) | `StartTimeMode`: STRICT/USER_SET/BY_START_STATION |
| Жеребьёвка | По забегам/коллективам/регионам, общая | По группам, по дистанциям (коридоры+зазор), общая с чередованием клубов |
| Электронная отметка | `SystemType`: SPORTIDENT/SFR/SPORTIDUINO/RFID_IMPINJ/SRPID/HUICHANG/MANUAL — аппаратные станции | `PunchingSystem`: те же SPORTIDENT/SFR/SPORTIDUINO + PENCIL/PUNCH, но чтение — NFC телефона |
| Проверка порядка КП | `ResultChecker.penalty_calculation_standard` — сложный diff (пропуски/лишние/дубли) | `checkControlPointOrderPro` |
| Ручная правка | Привязка нераспознанного чипа, ручной ввод | Ручной ввод старта/финиша, `CreditMissedCp` |
| Live-результаты | LiveOrg (локальный веб-сервер), orgeo.ru | `core:eventdetails`, поллинг 30с |
| Онлайн-синхронизация | Есть (другая архитектура — см. раздел 2) | `core:sync`, offline-first, server-wins |
| Экспорт | IOF XML (полный), HTML/docx шаблоны | CSV, PDF, публикация HTML + обратный импорт из HTML |

## 2. Есть у pysport, нет у нас — подтверждено чтением кода

### 2.1 Форматы гонки, которых у нас нет вообще

`RaceType` (`memory.py:67`): `INDIVIDUAL_RACE`, `PURSUIT`, `RELAY`, `MULTI_DAY_RACE`.

- **Эстафеты (RELAY)** — не просто enum-значение, а полноценная подсистема (`models/start/relay.py`, классы `RelayTeam`/`RelayLeg` в `memory.py:2519-2800+`): у команды несколько этапов (`legs`), у каждого этапа свой «вариант» дистанции (например, распределение по трассам A/B/C по этапам, разбор строки `"101.1: CB"`), старт следующего этапа автоматически берётся из финиша предыдущего (`set_start_time_from_previous`), номер участника кодирует этап и команду (`1000*leg + team_number`), есть `is_best_team_placing_mode`, клонирование команд (`relay_clone_dialog.py`), отдельный экран назначения номеров (`relay_number_dialog.py`). У нас в домене `Stage.kt` есть, но никаких `RELAY`/`relay` в коде не найдено (`grep` пустой) — эстафет нет совсем, не только «менее развиты».
- **Гонка преследования (PURSUIT)** — `Group.pursuit_start_time`: старт по результатам предыдущего этапа/квалификации. У нас такого поля нет.
- **Многодневные соревнования (MULTI_DAY_RACE)** — `Person.multi_day_id` (идентификация одного человека между днями по ФИО+группе), `Result.get_result_otime_current_day()`, отдельный статус `MULTI_DAY_ISSUE`. У нас накопительного мульти-дневного зачёта под одним событием нет (это не то же самое, что наш «рейтинг серий» — там разные соревнования и разный движок сопоставления).
- **Гандикап-старт и обратный старт** — подтверждено кодом (`gui/dialogs/start_handicap_dialog.py`, `models/start/start_preparation.py::handicap_start_time/reverse_start_time`): два режима — «Handicap» (старт от лидера с гэпом, `max_gap`, второй поток `second_start_time`, сдвиг после DSQ `dsq_offset`) и «Reverse» (лидер стартует последним). У нас в предыдущей версии документа было написано «этого нет и у них» — это была ошибка по недостатку данных; на самом деле гандикап **есть**, просто не было в документации.

### 2.2 Движок расчёта результата — значительно более гибкий

`sportorg/models/result/result_checker.py` — по объёму и вариативности заметно превосходит нашу проверку:

- **Free-order course** (score-O свободного порядка) с опциональными обязательными первым/последним КП (`40,*,*,90`) — считает пропуски/лишние с учётом дублей отдельным алгоритмом (`penalty_calculation_free_order`), не тем же, что у обычной классики.
- **Marked route (маркированная трасса)** — два разных режима штрафа: **штрафной круг** (physically running extra loop, засекается по отметке на специальной станции, `marked_route_penalty_lap_station_code`) или **штрафное время** (фиксированные минуты за ошибку, `marked_route_penalty_time`), плюс режим «без дисквалификации, только штраф» (`marked_route_dont_dsq`).
- **Рогейн (score/очки)** — не только штраф за минуту опоздания (это у нас тоже есть в `ParticipantGroup.scorePenaltyPerMinute`), но и: настраиваемый вес очков по КП (`ControlPoint.score`, а не единый штраф), режим «разрешить повторные отметки того же КП» (`allow_duplicates`), фиксированный порог `min_scores` для зачёта разряда.
- **ARDF (радиоориентирование/«охота на лис»)** — отдельный алгоритм расчёта очков с поддержкой «любого из группы КП» (`?(a,b,c)` синтаксис в коде дистанции). У нас такого вида спорта нет вообще (см. `KindOfSport`: только Orienteering/CrossCountrySki/TrailRunning).
- **Credit time** — вычитание времени, проведённого на определённом КП (например, пункт медпомощи/питания), из итогового результата — не идёт в зачёт. У нас такого нет.
- **Overtime как отдельный статус** — при превышении `group.max_time` статус `OVERTIME` (не `DSQ`), причём для score-режима есть отдельный допустимый «пере-раун» `max_overrun_time`, до которого ещё не превышение. У нас `timeLimitMinutes`/`maxLatenessMinutes` есть только для формата BY_CHOICE (рогейн-подобного), а для обычной классики (FORWARD) контрольного времени финиша с отдельным статусом OVERTIME нет вовсе.
- **Кубковая система очков** (`ScoreCalculation`, `scores_mode`: `off`/`array`(таблица очков по месту)/`formula`(очки по формуле от времени лидера, eval-выражение)) — считается на уровне одной гонки/группы, годится для локального «кубка этапов». Концептуально близко к нашему `feature:rating`, но встроено прямо в движок результата одного файла соревнования, а не как отдельная кросс-событийная сущность с клубами.

### 2.3 Статусы результата — заметно детальнее

`ResultStatus` (18 значений): `NONE, OK, FINISHED, DISQUALIFIED, MISSING_PUNCH, DID_NOT_FINISH, ACTIVE, INACTIVE, OVERTIME, SPORTING_WITHDRAWAL (снятие по показаниям здоровья), NOT_COMPETING (вне зачёта), MOVED, MOVED_UP, DID_NOT_START, DID_NOT_ENTER, CANCELLED, RESTORED, MISS_PENALTY_LAP, MULTI_DAY_ISSUE`.

У нас (`domain/.../ResultStatus.kt`): `REGISTERED, STARTED, FINISHED, DSQ, DNS, DNF` — 6 значений. Разница не только в количестве: `NOT_COMPETING`/`SPORTING_WITHDRAWAL`/`MOVED`(перемещён в другую группу)/`RESTORED` (восстановлен после снятия) — это реальные организаторские кейсы, которых у нас формально не описать.

### 2.4 Разряды (ЕВСК) — подтверждено кодом, не только маркетингом

`Qualification` (IntEnum: юн.III/II/I, III/II/I разряд, КМС, МС, МСМК) + `RankingItem`/`Ranking` — расчёт выполнения разряда по месту (`max_place`), времени (`max_time`) или проценту от времени/очков лидера (`percent`, `min_scores`), настраиваемая таблица очков в конфиге. У нас разрядов нет вовсе (не только «недоделаны» — концепции нет в домене).

### 2.5 Участник — несколько полей, которых нет у нас

`Person` (`memory.py:1346`): `is_paid` (оплата стартового взноса), `is_out_of_competition` (внеконкурсный участник — бежит вне своей возрастной группы), `is_rented_card`/`is_personal` (чип в аренду vs личный чип участника), `world_code`/`national_code` (международный/национальный код спортсмена для IOF/ЕВСК). Проверил наш домен (`grep` по `isPaid/entryFee/outOfCompetition/isRented`) — ничего из этого нет.

### 2.6 Teamwork — принципиально другая архитектура синхронизации

`sportorg/modules/teamwork/` (`client.py` 178, `server.py` 479, `crypto.py` 88, `packet_header.py` 157 строк) — это **не** HTTP REST к облаку, а собственный **шифрованный бинарный протокол клиент-сервер** для локальной сети: один оператор поднимает сервер, остальные подключаются напрямую по IP:порт, работает полностью без интернета вообще. У нас `core:sync` — это WorkManager + Retrofit к центральному облачному серверу, требует интернет рано или поздно, но зато не привязан к локальной сети/один оператор-хост. Разные компромиссы: pysport лучше для полностью офлайн-точки (лес без связи, несколько судейских ноутбуков рядом), мы — для распределённых устройств, которым не обязательно быть в одной Wi-Fi сети.

### 2.7 Recovery — 4 независимых источника восстановления при сбое

`sportorg/modules/recovery/`: `recovery_si_master_csv` (из лога мастер-станции SPORTident), `recovery_sportorg_si_log`, `recovery_orgeo_finish_csv` (из бэкапа онлайн-сервиса), `recovery_sportorg_html` (из уже опубликованной HTML-страницы результатов). У нас нет отдельного механизма восстановления результатов из внешних источников на случай потери локальной БД — только штатный Room + sync.

### 2.8 Прочее

- **Резервные участники** (reserves) в жеребьёвке — авто-добавление с заданным количеством/процентом на группу.
- **Аренда чипов** (`rent_cards_dialog.py`) как явный флоу, а не просто поле — у нас есть экраны выдачи/прошивки чипа, но не бизнес-флоу «аренда с возвратом/депозитом».
- **Telegram-интеграция** (`modules/telegram/telegram.py`) — уведомления через бота.
- **Плагинная система** (`modules/plugins/manager.py`, `plugin-example/` в репо) — сторонние расширения. Вероятно нерелевантно для мобильного приложения.
- **Печать** — по факту в шаблонах (`sportorg/data/templates/reports/`) всего 4 отчёта: результаты, старт-лист, старт-лист эстафеты, старт по командам + печать сплитов. Меньше, чем можно было подумать по документации (шахматка/протокол допуска отдельными файлами-шаблонами не найдены — возможно, генерируются иначе, не проверял до конца).

## 3. Есть у нас, нет у pysport

1. **NFC-считывание телефоном** вместо кабельных станций — принципиально другая модель разворачивания точки (дешевле на старте, ограничена радиусом NFC и требует по устройству на каждую точку отметки).
2. **Клубы и команды платформы** (`FOUNDER/ADMIN/MEMBER`, заявки на вступление) — у pysport `Organization` — это просто справочник коллективов/клубов текстом, без ролей, членства и жизненного цикла заявок.
3. **Рейтинг серий соревнований**, привязанный к клубу-владельцу, с маппингом групп между разными стартами и сопоставлением участника по userId/ФИО+ДР между разными файлами соревнований — у pysport «кубковая» система очков (2.2) считается только внутри одного файла/события, кросс-событийной сущности с собственным жизненным циклом нет.
4. **Профиль пользователя платформы** (email+OTP, история регистраций участника на соревнования как систематический сервис) — у pysport нет понятия «пользователь платформы», есть только «оператор программы» и «участник конкретного старта».
5. **Дневник тренировок с GPS-треком** (`feature:diary`) — не связан с соревнованиями вообще, у pysport такого пласта нет.
6. **Темп (pace) по перегонам КП** по длине перегона из карты дистанции (`SEN-58`) — в коде pysport (`result_calculation.py`, `split_calculation.py`) считается только время и место, темп по метражу перегона не нашёл.
7. **График гонки** (`race_graph`) — не нашёл аналога в pysport.
8. **Offline-first с сервер-облаком** и конфликт-резолюцией server-wins на нестабильной мобильной сети — другой сценарий устойчивости, чем LAN teamwork у pysport (см. 2.6).
9. **Мультиплатформенная поставка через сторы** (gplay/rustore/huawei) — pysport это desktop `.exe`/`.pyw` под Windows.
10. **Несколько видов спорта в одной модели** (`Orienteering`, `CrossCountrySki`, `TrailRunning`) — у pysport специализация только на ориентировании/рогейне/ARDF/маркированной трассе (плюс упомянутый в GUI `swimming_results.py` — вероятно частный кастом, не основной фокус).
11. **Продуктовая аналитика** (AppMetrica+Firebase) — у desktop pysport такого пласта нет и не нужно.

## Как читать этот список

Раздел 2 — это уже не предположения из документации, а прямые находки в коде (`sportorg/models/memory.py`, `models/start/*`, `models/result/*`, `modules/teamwork/*`, `modules/recovery/*`). Самые весомые кандидаты на рассмотрение:

- **Эстафеты** (2.1) и **гандикап/pursuit-старт** (2.1) — вписываются в NFC-модель без архитектурных проблем, это чисто доменная логика старта/расчёта.
- **Более гибкий движок штрафов** (маркированная трасса с двумя видами наказания, credit time, overtime-статус, ARDF) — расширение существующего `OrienteeringDirection`/`ResultChecker`-аналога, не требует новой инфраструктуры.
- **Расширенные статусы результата** (2.3) — механическое расширение enum + бизнес-правил, низкая архитектурная сложность.
- **LAN teamwork без интернета вовсе** (2.6) и **recovery из внешних источников** (2.7) — самые сложные по архитектуре пункты; стоит явно решить, нужен ли сценарий «совсем без интернета, несколько устройств рядом», раз у нас телефон, а не ноутбук с кабельной станцией.
